## 一、整体学习顺序与判断标准

严格顺序：**LangChain 核心抽象 → LangGraph 编排 → MCP 协议 → 记忆与多 Agent → 工程化架构与成本性能（网关/上下文工程/状态管理/缓存/批处理/路由）→ 安全与反馈追踪 → 部署 → RAG 检索优化 → RAGAS 评估**。

原因：
- **先 LangChain 再 LangGraph**：LangGraph 是同一个团队在 LangChain 的 `Runnable`/LCEL 编程模型基础上加了"循环 + 显式状态"两样东西，不先搞懂 LCEL 管道（`prompt | model | parser`），直接学 LangGraph 会把两层抽象混在一起，出问题时分不清是哪一层的锅。
- **再补 Agent 的骨架**：LangGraph 编排、MCP 协议、多 Agent 协作解决的是"怎么组织复杂流程"。
- **然后补工程化架构与成本性能**：模型网关/上下文工程/状态管理决定了系统怎么组织信息和请求，缓存/批处理/分级路由决定了同样的效果能不能花更少的钱更快跑完——这两块紧密相关，网关是把路由、限流收拢到一层的架构方式，所以排在一起学。
- **安全和反馈追踪、部署跟着补齐**：决定系统能不能被信任、能不能公开跑。
- **最后做 RAG**：这条线相对独立，放在最后不影响前面的学习。

三条大路线（A/C/B）彼此耦合度低，谁先谁后主要取决于"哪个是当前项目最大的短板"；本路线按 A→C→B 顺序系统覆盖，若中途发现某条线对你当前项目更紧迫，可以调整顺序单独先做。

### Day 38：理解 MCP（Model Context Protocol）

学习重点：
- MCP 的三种核心能力：Resources（数据）、Tools（可调用工具）、Prompts（提示词模板）
- Server / Client 角色划分，和"直接把函数注册给模型"的区别是什么
- MCP vs OpenAI function calling 的定位差异：function calling 是"模型层"的约定（JSON Schema 工具定义，由模型决定何时触发），MCP 是"连接层"的协议（独立进程、跨语言、可复用的工具服务器）——两者不是替代关系，MCP Server 本身通过 function calling 把工具暴露给模型
- A2A（Agent-to-Agent）协议简介：Google DeepMind 在 2025 年发布的 Agent 间协作标准，与 MCP 并列，MCP 管"模型与工具/数据的连接"，A2A 管"Agent 与 Agent 的任务委派与状态同步"——Day 41 会深入用到，今天先建立边界感

### Day 46：批处理（Batching）

学习重点：
- 什么场景适合批处理：大批量、非实时的请求（如批量生成摘要、批量打标签），用批处理换吞吐量和成本
- 和缓存/路由的区别：缓存省的是"重复请求"，路由省的是"用错模型"，批处理省的是"单次请求的固定开销"（连接建立、并发调度、Prompt 前缀重复处理）
- 常见实现方式：并发发起多个请求 + 限速控制；部分厂商提供专门的 Batch API（异步提交、延迟更高但价格更低）

- **实现方式 A**：Python `asyncio` 并发 + `asyncio.Semaphore` 限速（适用于所有 Provider，延迟低）
- **实现方式 B（可选）**：若当前使用的 Provider 有专用 Batch API（如 Anthropic Batch API、OpenAI Batch API——异步提交、通常有 50% 折扣但需等候），尝试接入并对比两种方式的延迟/成本差异

## 五、常见误区（深化阶段特有）

1. **框架崇拜**：引入 LangChain/LangGraph/MCP 不是为了"用最新技术"，而是解决手写代码在组装标准化、状态管理、持久化、协作上的具体痛点——如果项目简单到手写完全够用，不必强行引入框架。
2. **跳过 LangChain 直接学 LangGraph**：LangGraph 的 Node 建立在 LangChain 的 `Runnable`/LCEL 模型之上，跳过 Day 31–32 直接学 Day 33 会经常分不清某个报错是 LangGraph 的问题还是底层 LCEL 的问题。
3. **工程化架构一步到位**：模型网关、上下文工程、状态管理这些不是"越复杂越好"，单用户小项目未必需要独立网关层——按 Day 52 的复盘标准判断值不值得投入，而不是照单全收。
4. **可观测性拖到最后才补**：等项目出问题了才想起接 LangFuse，往往已经错过了复现问题的窗口——可观测性应该在功能稳定后立刻补上，而不是等出事。
5. **只优化检索不评估**：加了 Reranker/HyDE 但没有评估集，无法证明真的变好了——任何 RAG 优化手段都要有 RAGAS 或自建评估集的数字支撑。
6. **安全防护一次性做完就不管**：Prompt 注入手法会持续演化，红队测试应该是每次改动后的常规检查项，不是一次性任务。
7. **反馈收集了但没有回流**：加了 👍/👎 按钮却从不看这些数据，等于没做——反馈追踪的价值在于真正被用来筛出低分 case、驱动下一轮迭代。
8. **批处理和缓存/路由混为一谈**：三者都是"降本"手段，但省的是不同的钱（缓存省重复请求，批处理省单次开销，路由省用错模型的钱）——上生产前最好三者都评估一遍，而不是做了一个就以为够了。
9. **Agent 过度设计**：遇到稍复杂的任务，就想套 Planner + Executor + Critic 三 Agent 架构——多数时候，一个 LangGraph 节点加几条工具调用就能解决的问题，不需要上多 Agent 协同。引入多 Agent 的判断标准是：任务是否可以真正拆解成**相互独立、可并行**的子任务，且各子任务的输入/输出对彼此是黑盒；若不是，单 Agent + 更好的 Prompt + 更清晰的工具定义往往更可靠、更易调试、出错时更好追溯。
