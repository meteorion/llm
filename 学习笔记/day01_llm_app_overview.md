## 一、什么是大模型应用开发

### 1.1 定义

大模型应用开发是指：**将预训练好的大语言模型（LLM）通过 API 接入实际业务场景，构建能够理解自然语言、生成内容、执行任务的智能应用**。

### 1.2 核心特点

| 特点 | 说明 |
|------|------|
| **不训练模型** | 直接使用云端的预训练模型，通过 API 调用 |
| **以 Prompt 为核心** | 通过设计提示词来控制模型行为 |
| **快速迭代** | 无需深度学习背景，传统开发者即可上手 |
| **按量付费** | 根据使用量（Token 数）计费，降低试错成本 |

### 1.3 与传统开发的关系

```
传统开发：用户输入 → 规则/逻辑处理 → 固定输出
大模型应用：用户输入 → Prompt + 模型推理 → 灵活的自然语言输出
```

大模型应用不是替代传统开发，而是在需要理解语义、生成内容、处理非结构化数据的场景中提供新的解决方案。

### 1.4 典型应用场景

| 场景 | 示例 |
|------|------|
| **智能客服** | 理解用户问题，自动回答或转人工 |
| **文档问答** | 基于企业知识库回答员工问题 |
| **内容生成** | 自动写邮件、生成报告、创作文案 |
| **信息抽取** | 从简历、合同中提取关键信息 |
| **代码辅助** | 代码补全、代码解释、Bug 修复 |
| **数据分析** | 自然语言查询数据库，生成图表 |

## 二、大模型基础知识点

### 2.1 什么是大语言模型（LLM）

#### 2.1.1 定义

大语言模型（Large Language Model，LLM）是一种基于深度学习的 AI 模型，通过在海量文本数据上进行训练，学习语言的统计规律和语义知识，从而具备理解和生成自然语言的能力。

#### 2.1.2 "大"体现在哪里

| 维度 | 说明 | 典型规模 |
|------|------|---------|
| **参数量** | 模型的可学习参数数量 | 7B、70B、175B、1.8T |
| **训练数据** | 用于训练的文本量 | TB 级别的文本数据 |
| **计算资源** | 训练所需算力 | 数千张 GPU，训练数周 |

**参数量对比：**
```
GPT-2 (2019)      : 15 亿参数 (1.5B)
GPT-3 (2020)      : 1750 亿参数 (175B)
GPT-4 (2023)      : 约 1.8 万亿参数 (1.8T，未官方确认)
Llama-2-70B       : 700 亿参数 (70B)
Qwen-Max          : 千亿级参数
```

#### 2.1.3 大模型的核心能力

| 能力 | 说明 | 示例 |
|------|------|------|
| **语言理解** | 理解文本含义、意图、情感 | 阅读理解、意图识别 |
| **语言生成** | 生成流畅、连贯的文本 | 写作、对话、翻译 |
| **知识推理** | 基于内部知识进行逻辑推理 | 问答、分析、决策 |
| **代码能力** | 理解和生成代码 | 代码补全、Debug |
| **多语言** | 跨语言理解和生成 | 翻译、多语言问答 |

### 2.3 大模型的工作原理

#### 2.3.1 核心架构：Transformer

Transformer 是现代大模型的基础架构，核心是**自注意力机制（Self-Attention）**。

```
┌─────────────────────────────────────────────────────────────────┐
│                    Transformer 工作原理（简化版）                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│   输入文本："我 爱 北京"                                          │
│       │                                                          │
│       ▼                                                          │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │              Tokenizer（分词器）                          │  │
│   │   "我" → Token_101, "爱" → Token_3421, "北京" → Token_782 │  │
│   └─────────────────────────────────────────────────────────┘  │
│       │                                                          │
│       ▼                                                          │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │              Embedding（词嵌入）                          │  │
│   │   Token → 高维向量（如 4096 维）                          │  │
│   │   每个 Token 变成一个有语义的向量                         │  │
│   └─────────────────────────────────────────────────────────┘  │
│       │                                                          │
│       ▼                                                          │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │         Self-Attention（自注意力机制）                    │  │
│   │                                                          │  │
│   │   核心思想：每个词"关注"其他所有词                         │  │
│   │                                                          │  │
│   │   "我" 关注 "爱" → 理解"我"是爱的主体                     │  │
│   │   "爱" 关注 "北京" → 理解"北京"是爱的对象                  │  │
│   │                                                          │  │
│   │   让模型理解词与词之间的关系                              │  │
│   └─────────────────────────────────────────────────────────┘  │
│       │                                                          │
│       ▼                                                          │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │              多层 Transformer Block                       │  │
│   │                                                          │  │
│   │   Block 1: 初步理解                                       │  │
│   │   Block 2: 更深层语义                                     │  │
│   │   Block 3: 上下文整合                                     │  │
│   │   ...                                                     │  │
│   │   Block N: 高层抽象理解                                   │  │
│   │                                                          │  │
│   │   层数越多，理解越深入（GPT-4 有上百层）                   │  │
│   └─────────────────────────────────────────────────────────┘  │
│       │                                                          │
│       ▼                                                          │
│   ┌─────────────────────────────────────────────────────────┐  │
│   │              输出层（预测下一个 Token）                    │  │
│   │                                                          │  │
│   │   给词表中每个词打分，表示成为下一个词的概率               │  │
│   │                                                          │  │
│   │   "天安门" → 0.35                                         │  │
│   │   "的"    → 0.25                                         │  │
│   │   "人"    → 0.12                                         │  │
│   │   ...                                                     │  │
│   └─────────────────────────────────────────────────────────┘  │
│       │                                                          │
│       ▼                                                          │
│   采样输出 → "天安门"                                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### 2.3.2 训练过程

大模型的训练分为三个阶段：

```
┌─────────────────────────────────────────────────────────────────┐
│                        大模型训练三阶段                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  阶段一：预训练（Pre-training）                                   │
│  ─────────────────────────────────                              │
│  目标：学习语言的统计规律和世界知识                               │
│                                                                  │
│  数据：海量文本（网页、书籍、代码、论文等）                        │
│        数万亿 Token，TB 级数据                                   │
│                                                                  │
│  任务：预测下一个词（Next Token Prediction）                      │
│        "今天天气真" → 预测 "好"                                   │
│                                                                  │
│  结果：获得一个"懂语言、有知识"的基座模型（Base Model）            │
│        但还不会很好地"对话"或"遵循指令"                          │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  阶段二：监督微调（SFT，Supervised Fine-Tuning）                   │
│  ───────────────────────────────────────────                    │
│  目标：让模型学会遵循指令、进行对话                               │
│                                                                  │
│  数据：高质量的指令-回复对                                        │
│        人工编写或筛选的对话数据                                   │
│                                                                  │
│  示例：                                                          │
│    Input: "请用一句话介绍北京"                                    │
│    Output: "北京是中国的首都，拥有悠久的历史和丰富的文化遗产。"     │
│                                                                  │
│  结果：模型学会"问答"、"对话"等交互方式                           │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  阶段三：人类反馈强化学习（RLHF）                                 │
│  ─────────────────────────────────────                          │
│  目标：让模型输出更符合人类偏好                                   │
│                                                                  │
│  流程：                                                          │
│    1. 人类对模型的多个回答进行排序                                │
│    2. 训练一个奖励模型（Reward Model）学习人类偏好                │
│    3. 用强化学习优化大模型，使其输出得分更高                      │
│                                                                  │
│  结果：模型回答更安全、更有帮助、更符合人类期望                    │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### 2.3.3 模型推理

推理是使用训练好的模型生成输出的过程：

```
推理过程：
1. 输入处理：将用户输入转为 Token 序列
2. 前向传播：Token 序列经过模型计算
3. 预测输出：计算下一个 Token 的概率分布
4. 采样策略：根据概率选择下一个 Token
5. 循环生成：将生成的 Token 加入输入，继续生成
6. 停止条件：遇到结束符或达到最大长度

示例：
输入："1+1="
Step 1: 预测下一个 Token，概率最高的是 "2"
输出："2"
Step 2: 输入变成 "1+1=2"，预测下一个，概率最高的是 "<end>"
结束
```

#### 2.3.4 采样参数

控制模型生成多样性的关键参数：

| 参数 | 说明 | 范围 | 影响 |
|------|------|------|------|
| **Temperature** | 控制输出的随机性 | 0-2 | 低=确定性高，高=创造性高 |
| **Top-P** | 核采样，从概率累计达到 P 的候选中选 | 0-1 | 控制候选词范围 |
| **Top-K** | 从概率最高的 K 个候选中选 | 1-100 | 限制候选词数量 |
| **Max Tokens** | 最大生成长度 | 正整数 | 控制输出长度 |

**Temperature 详解：**
```
Temperature = 0：
  - 几乎确定性输出
  - 适合：事实问答、代码生成、格式化输出

Temperature = 0.7：
  - 平衡确定性和创造性
  - 适合：日常对话、写作辅助

Temperature = 1.0+：
  - 更有创造性、多样性
  - 适合：创意写作、头脑风暴
```

```
│     解决方案：代码执行、思维链提示、使用推理模型                   │
│                                                                  │
│  4. 无法访问实时信息                                             │
│     ─────────────────                                           │
│     不知道实时天气、股价、新闻等                                  │
│                                                                  │
│     解决方案：Tool Calling 调用外部 API                          │
│                                                                  │
│  5. 缺乏真正理解                                                 │
│     ───────────────                                             │
│     本质上是概率预测，没有真正的"理解"和"意识"                    │
│                                                                  │
│     应对：理解模型本质，不期望其具备真正智能                       │
│                                                                  │
│  6. 安全与偏见                                                   │
│     ────────────                                                │
│     可能输出有害内容或有偏见的内容                                │
│                                                                  │
│     解决方案：安全审查、内容过滤、RLHF                            │
│                                                                  │
│  7. 上下文窗口限制                                               │
│     ────────────────                                            │
│     无法一次性处理超长文本                                        │
│                                                                  │
│     解决方案：文档切分、RAG、摘要压缩                             │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### 2.5.3 幻觉问题详解

```
幻觉类型：

1. 事实性幻觉
   问：明朝第一位皇帝是谁？
   答：明朝第一位皇帝是朱元璋，年号洪武。（正确）

   问：明朝第五位皇帝是谁？
   答：明朝第五位皇帝是朱瞻基。（可能错误，需要核实）

2. 来源幻觉
   模型可能编造不存在的：
   - 书籍、论文、新闻报道
   - 法律条款、政策文件
   - 名人名言、历史事件

3. 数据幻觉
   编造不存在的：
   - 统计数据
   - 实验结果
   - 财务数据

减少幻觉的策略：
- 使用 RAG 基于真实文档回答
- 要求模型标注信息来源
- 对关键信息进行人工核查
- 使用"如果你不确定，请说明"的提示
```

## 三、核心概念详解

### 3.1 Prompt（提示词）

#### 3.1.1 什么是 Prompt

Prompt 是用户发送给模型的文本指令，是人与大模型交互的核心方式。模型根据 Prompt 理解任务意图，并生成相应的输出。

#### 3.1.2 Prompt 的组成要素

一个完整的 Prompt 通常包含以下要素：

```
┌─────────────────────────────────────────────────────┐
│                     Prompt 结构                      │
├─────────────────────────────────────────────────────┤
│  1. 角色设定（Role）                                  │
│     "你是一个专业的翻译助手"                          │
│                                                      │
│  2. 任务描述（Task）                                  │
│     "将下面的中文翻译成英文"                          │
│                                                      │
│  3. 上下文信息（Context）                             │
│     "这是一篇科技新闻，涉及人工智能领域"               │
│                                                      │
│  4. 输入数据（Input）                                 │
│     "原文：{待翻译文本}"                              │
│                                                      │
│  5. 输出约束（Constraints）                          │
│     "只输出翻译结果，不要添加任何解释"                 │
│                                                      │
│  6. 示例（Few-shot Examples）                        │
│     "示例：你好 → Hello"                             │
└─────────────────────────────────────────────────────┘
```

#### 3.1.3 Prompt 示例对比

**差的 Prompt：**
```
帮我总结这篇文章
```

**好的 Prompt：**
```
你是一个专业的科技媒体编辑。请对下面的文章进行摘要，要求：
1. 摘要长度控制在 100-150 字
2. 突出核心观点和关键数据
3. 使用客观、简洁的语言
4. 保持原文的逻辑顺序

文章内容：
{文章全文}
```

#### 3.1.4 Prompt 设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **明确具体** | 避免模糊表达 | "用 3 句话总结" 而非 "简要总结" |
| **角色设定** | 赋予模型特定身份 | "你是一位资深律师" |
| **提供示例** | 用例子说明期望格式 | Few-shot learning |
| **约束输出** | 指定格式、长度、风格 | "以 JSON 格式输出" |
| **分解任务** | 复杂任务拆成多步 | "第一步...第二步..." |

---

### 3.2 Token（词元）

#### 3.2.1 什么是 Token

Token 是大模型处理文本的最小单位。模型不直接理解字符，而是将文本切分成 Token 序列进行处理。

#### 3.2.2 Token 与文本的换算

| 语言 | 换算规则（约） |
|------|---------------|
| 英文 | 1 Token ≈ 0.75 个单词 |
| 中文 | 1 Token ≈ 1-2 个汉字 |

**示例：**

```
英文："Hello, how are you?" → 约 6 个 Token
中文："你好，最近怎么样？" → 约 8-10 个 Token
```

#### 3.2.3 为什么 Token 很重要

**1. 成本计算**

| 模型 | 输入价格（每 1M Token） | 输出价格（每 1M Token） |
|------|------------------------|------------------------|
| GPT-4o | $2.50 | $10.00 |
| GPT-4o-mini | $0.15 | $0.60 |
| Claude 3.5 Sonnet | $3.00 | $15.00 |
| Qwen-Turbo | ¥0.3 | ¥0.6 |

> 价格仅供参考，以官方最新价格为准

**成本估算示例：**
```
假设：
- 每次请求平均输入 1000 Token
- 每次请求平均输出 500 Token
- 每天 1000 次调用

使用 GPT-4o-mini 的日成本：
输入：1000 × 1000 × 0.15 / 1,000,000 = $0.15
输出：1000 × 500 × 0.60 / 1,000,000 = $0.30
日总成本：$0.45
月成本（30天）：$13.5
```

**2. 上下文限制**

| 模型 | 上下文窗口 |
|------|-----------|
| GPT-4o | 128K Token |
| GPT-4o-mini | 128K Token |
| Claude 3.5 Sonnet | 200K Token |
| Qwen-Max | 32K Token |

超过限制会导致：
- 早期对话内容被截断
- 长文档无法完整处理
- RAG 检索结果无法全部放入

#### 3.2.4 Token 优化策略

| 策略 | 说明 |
|------|------|
| 精简 Prompt | 去除不必要的描述 |
| 压缩历史对话 | 只保留关键信息 |
| 分批处理长文本 | 避免一次性输入过长 |
| 选择合适的模型 | 简单任务用小模型 |

---

### 3.3 上下文窗口（Context Window）

#### 3.3.1 什么是上下文窗口

上下文窗口是模型一次能处理的最大 Token 数量，包括：
- 系统提示词（System Prompt）
- 历史对话记录
- 用户当前输入
- 模型已生成的输出

#### 3.3.2 上下文窗口的结构

```
┌────────────────────────────────────────────────────────┐
│                    上下文窗口                           │
├────────────────────────────────────────────────────────┤
│  System Prompt（系统提示）                              │
│  "你是一个有帮助的助手..."                              │
│  ────────────────────────────────────────              │
│  历史消息 1                                             │
│  User: "今天天气怎么样？"                               │
│  Assistant: "请问您在哪个城市？"                        │
│  ────────────────────────────────────────              │
│  历史消息 2                                             │
│  User: "北京"                                          │
│  Assistant: "北京今天晴，气温 25°C..."                  │
│  ────────────────────────────────────────              │
│  当前输入                                               │
│  User: "明天呢？"                                       │
│  ────────────────────────────────────────              │
│  待生成                                                 │
│  Assistant: [模型正在生成...]                           │
└────────────────────────────────────────────────────────┘
```

#### 3.3.3 上下文溢出的处理

当对话超过上下文窗口限制时，常见处理方式：

| 方式 | 说明 | 优缺点 |
|------|------|--------|
| **截断** | 丢弃最早的对话 | 简单，但丢失信息 |
| **滑动窗口** | 只保留最近 N 轮 | 平衡效果和成本 |
| **摘要压缩** | 对历史对话生成摘要 | 保留关键信息，增加处理成本 |
| **向量检索** | 将历史存入向量库，按需检索 | 复杂但效果好 |

---

### 3.4 Embedding（嵌入/向量化）

#### 3.4.1 什么是 Embedding

Embedding 是将文本转换为高维向量的过程。向量是一个数字数组，例如：

```
"人工智能" → [0.23, -0.45, 0.78, 0.12, ..., -0.34]  (1536维)
```

核心思想：**语义相似的文本，其向量在空间中的距离更近**。

#### 3.4.2 Embedding 的作用

```
传统关键词搜索：
  用户搜索："苹果手机"
  只能匹配包含"苹果"或"手机"的文档
  无法匹配："iPhone 15 Pro Max"

语义搜索（Embedding）：
  用户搜索："苹果手机"
  可以匹配：
    - "iPhone 15 Pro Max"
    - "Apple 最新款智能手机"
    - "iOS 设备推荐"
  因为这些文本的语义相近，向量距离近
```

#### 3.4.3 相似度计算

最常用的是**余弦相似度**：

```
相似度 = cos(θ) = (A · B) / (|A| × |B|)

结果范围：[-1, 1]
- 1: 完全相同方向
- 0: 无相关性
- -1: 完全相反
```

#### 3.4.4 Embedding 的应用场景

| 场景 | 说明 |
|------|------|
| **语义搜索** | 根据含义而非关键词检索 |
| **推荐系统** | 找相似内容进行推荐 |
| **聚类分析** | 将相似文本分组 |
| **RAG 检索** | 从知识库中检索相关文档 |

#### 3.4.5 常见 Embedding 模型

| 模型 | 维度 | 特点 |
|------|------|------|
| text-embedding-3-small | 1536 | OpenAI，性价比高 |
| text-embedding-3-large | 3072 | OpenAI，效果更好 |
| bge-large-zh | 1024 | 中文效果好，可本地部署 |
| m3e-base | 768 | 中文开源，轻量级 |

---

### 3.5 RAG（检索增强生成）

#### 3.5.1 什么是 RAG

RAG = Retrieval-Augmented Generation（检索增强生成）

核心思想：**先从知识库检索相关信息，再将检索结果作为上下文提供给模型，让模型基于这些信息生成回答**。

#### 3.5.2 为什么需要 RAG

| 问题 | RAG 的解决方案 |
|------|---------------|
| 模型知识有截止日期 | 可以检索最新信息 |
| 模型不知道企业内部知识 | 可以检索私有文档 |
| 模型可能"幻觉"编造 | 基于真实文档回答 |
| 上下文窗口有限 | 只检索相关片段 |

#### 3.5.3 RAG 工作流程

```
┌─────────────────────────────────────────────────────────────────┐
│                        RAG 完整流程                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  【离线阶段：构建知识库】                                         │
│                                                                  │
│   原始文档 ──→ 文档切分 ──→ Embedding 向量化 ──→ 存入向量库        │
│     │            │              │                 │              │
│   PDF/Word    Chunk 1        [0.1,0.2,...]     向量数据库          │
│     │            │              │                 │              │
│   TXT/MD      Chunk 2        [0.3,0.4,...]      (Chroma/         │
│     │            │              │              FAISS/Milvus)     │
│              Chunk 3        [0.5,0.6,...]                        │
│                                                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  【在线阶段：问答流程】                                           │
│                                                                  │
│   用户问题                                                       │
│      │                                                           │
│      ▼                                                           │
│   问题 Embedding ──→ 向量相似度检索 ──→ 返回 Top-K 相关片段        │
│      │                    │                    │                 │
│   [0.2,0.3,...]      计算 cos 相似度         Chunk 1, Chunk 3    │
│                                                (最相关的 K 个)    │
│      │                                           │               │
│      ▼                                           ▼               │
│   ┌─────────────────────────────────────────────────────┐       │
│   │                     构建 Prompt                      │       │
│   │                                                      │       │
│   │   System: 你是一个助手，请基于以下参考资料回答问题    │       │
│   │                                                      │       │
│   │   参考资料：                                         │       │
│   │   {检索到的文档片段}                                 │       │
│   │                                                      │       │
│   │   用户问题：{用户问题}                               │       │
│   └─────────────────────────────────────────────────────┘       │
│      │                                                           │
│      ▼                                                           │
│   大模型生成回答                                                  │
│      │                                                           │
│      ▼                                                           │
│   输出答案 + 可选的引用来源                                        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### 3.5.4 RAG 的关键环节

| 环节 | 说明 | 影响因素 |
|------|------|---------|
| **文档切分** | 将长文档切成小片段 | Chunk 大小、重叠长度 |
| **向量化** | 文本转向量 | Embedding 模型选择 |
| **检索** | 找相似片段 | Top-K 数量、相似度阈值 |
| **上下文构建** | 组装 Prompt | 模板设计、信息排序 |
| **生成** | 模型回答 | 模型能力、约束设置 |

#### 3.5.5 文档切分详解

**为什么要切分？**
- 整篇文档太长，超过上下文窗口
- 检索精度：小片段更容易精确匹配

**切分参数：**

```
Chunk Size（块大小）：每个片段的 Token 数
  - 太小：语义不完整
  - 太大：检索精度下降
  - 推荐：200-500 Token

Chunk Overlap（块重叠）：相邻片段重叠的 Token 数
  - 避免关键信息被截断
  - 推荐：Chunk Size 的 10-20%
```

**切分示意：**

```
原文：这是一段很长的文档内容...

┌──────────────┐
│  Chunk 1     │
│  (300 Token) │
└──────┬───────┘
       │ ← 重叠部分
       ▼
┌──────────────┐
│  Chunk 2     │
│  (300 Token) │
└──────┬───────┘
       │
       ▼
      ...
```

### 3.6 Tool Calling（工具调用）

#### 3.6.1 什么是 Tool Calling

Tool Calling 让大模型能够调用外部工具或 API 来执行具体任务，从"只会说话"变成"能做事"。

#### 3.6.2 Tool Calling vs 普通对话

```
普通对话：
  用户："北京今天天气怎么样？"
  模型："抱歉，我无法获取实时天气信息..."

Tool Calling：
  用户："北京今天天气怎么样？"
  模型：[判断需要调用天气工具] → 调用 get_weather("北京")
  工具返回：{"temp": 25, "weather": "晴"}
  模型："北京今天天气晴朗，气温 25°C，适合外出活动。"
```

#### 3.6.3 Tool Calling 工作流程

```
┌───────────────────────────────────────────────────────────────┐
│                    Tool Calling 流程                           │
├───────────────────────────────────────────────────────────────┤
│                                                                │
│  1. 用户发送问题                                                │
│     │                                                          │
│     ▼                                                          │
│  2. 模型分析问题，判断是否需要调用工具                            │
│     │                                                          │
│     ├── 不需要 → 直接生成回答                                   │
│     │                                                          │
│     └── 需要 → 决定调用哪个工具，提取参数                        │
│                │                                               │
│                ▼                                               │
│  3. 返回工具调用请求                                            │
│     {                                                          │
│       "tool_name": "get_weather",                              │
│       "arguments": {"city": "北京"}                            │
│     }                                                          │
│                │                                               │
│                ▼                                               │
│  4. 应用层执行工具调用                                          │
│     result = get_weather("北京")                               │
│                │                                               │
│                ▼                                               │
│  5. 将工具结果返回给模型                                        │
│     {                                                          │
│       "role": "tool",                                          │
│       "content": "{\"temp\": 25, \"weather\": \"晴\"}"         │
│     }                                                          │
│                │                                               │
│                ▼                                               │
│  6. 模型基于工具结果生成自然语言回答                              │
│     "北京今天天气晴朗，气温 25°C..."                             │
│                                                                │
└───────────────────────────────────────────────────────────────┘
```

#### 3.6.4 工具定义示例

```python
tools = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "获取指定城市的天气信息",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "城市名称，如：北京、上海"
                    }
                },
                "required": ["city"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "search_web",
            "description": "搜索互联网获取信息",
            "parameters": {
                "type": "object",
                "properties": {
                    "query": {
                        "type": "string",
                        "description": "搜索关键词"
                    }
                },
                "required": ["query"]
            }
        }
    }
]
```

#### 3.6.5 常见工具类型

| 工具类型 | 示例 |
|---------|------|
| **信息查询** | 天气查询、股票行情、汇率转换 |
| **知识库检索** | 企业文档搜索、产品信息查询 |
| **数据库操作** | SQL 查询、数据统计 |
| **API 调用** | 发送邮件、创建工单、下单 |
| **代码执行** | 运行 Python 代码、数学计算 |

#### 3.6.6 Tool Calling 与 Agent 的关系

```
Tool Calling：单次工具调用能力

Agent：具备 Tool Calling 能力 + 规划能力 + 多步推理能力

示例：用户 "帮我查一下北京明天的天气，如果下雨就推荐室内活动"

Agent 工作流程：
  1. 规划：需要查天气，然后根据结果决定下一步
  2. 调用 get_weather("北京", "明天")
  3. 分析结果：下雨
  4. 调用 search_web("北京室内活动推荐")
  5. 整合信息，生成回答
```

## 七、常见问题

### Q1：大模型应用开发和传统软件开发有什么区别？

| 维度 | 传统开发 | 大模型应用开发 |
|------|---------|---------------|
| 输入处理 | 结构化输入 | 自然语言输入 |
| 输出确定性 | 输出固定 | 输出有随机性 |
| 核心能力 | 算法和数据结构 | Prompt 设计和流程编排 |
| 调试方式 | 断点、日志 | 观察输出、调整 Prompt |

### Q2：为什么强调先学原生 API 而不是直接用 LangChain？

理解原生 API 后，你能：
- 清楚消息结构和流转过程
- 准确排查问题所在
- 理解框架封装的原理
- 不被框架限制思路

### Q3：Token 计费会很贵吗？

对于学习和 Demo 阶段：
- 使用小模型（如 GPT-4o-mini），成本很低
- 精简 Prompt，减少不必要的 Token
- 控制输出长度

实际开发时：
- 做好成本预估
- 加入缓存机制
- 监控 Token 消耗
