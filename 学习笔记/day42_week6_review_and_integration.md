## 二、Day 27 原项目的短板与升级方案

### 2.1 原项目的四个短板

Day 27 的个人助理项目（天气 + 汇率 + 知识库）是一个经典单 Agent 实现：工具注册在应用代码里、每次启动记忆清空、所有步骤集中在一个 while 循环 ReAct 里。

| 短板 | 表现 | 严重程度 |
|-----|------|---------|
| **工具和应用耦合** | 天气/汇率工具写死在项目里，换个 AI 应用要复制粘贴代码 | 中 |
| **无跨会话记忆** | 用户每次重启都要重新说"我在北京"、"我用美元" | 高（直接影响用户体验） |
| **单 Agent 规划瓶颈** | 复合问题（"帮我规划行程，需要天气+汇率+路线"）容易漏步或顺序混乱 | 中 |
| **流程不可观测** | while 循环里看不清"现在执行到哪一步"，调试靠 print | 中 |

## 三、复盘问题 1：MCP 的收益边界在哪里

**问：引入 MCP 之后，工具调用的代码量明显增加了（需要维护 Server + 配置文件）。什么情况下 MCP 的收益能覆盖这个成本？**

**答**：MCP 的核心收益是**工具复用**——同一个工具服务器被多个 AI 应用使用。收益覆盖成本的判断标准：

| 场景 | 是否值得引入 MCP |
|-----|---------------|
| 只有一个 AI 应用使用这些工具，且工具用 Python 写 | ❌ 手写 `@tool` 更简单 |
| 同一套工具需要被 2 个以上应用使用（如 Claude Code + 自写 Agent） | ✅ MCP Server 一次实现，多处接入 |
| 工具需要用非 Python 语言实现 | ✅ MCP 跨语言特性发挥价值 |
| 需要把工具权限和应用权限分开控制 | ✅ 独立进程 = 独立权限沙箱 |
| 原型阶段，工具逻辑还在频繁变动 | ❌ 先手写，稳定后再迁移 MCP |

**今天的项目**：天气/汇率工具已经在 Day 39 做成了 MCP Server，Claude Code 也在用同一个 Server——这正是"多个 Client 共享"的场景，引入有价值。

## 四、复盘问题 2：长期记忆与工具调用应该如何配合

**问：长期记忆（System Prompt 注入偏好）和工具调用（模型决定何时查天气）是两个独立机制。它们有没有交叉或冲突的地方？实际项目里应该如何划分职责？**

**答**：两者解决不同的问题，分工清晰：

| 机制 | 解决什么 | 数据流向 |
|-----|---------|---------|
| **长期记忆 + System Prompt** | "模型应该知道但不用实时查的固定信息"（用户偏好、常用城市） | 存入 JSON → 注入 System Prompt → 模型直接使用，无需调用工具 |
| **工具调用** | "需要实时获取的动态数据"（当前天气、实时汇率） | 模型判断触发 → 调工具 → 拿到最新数据 |

**可能的冲突点**：记忆里有"常用城市：北京"，工具调用时用户又说"查上海天气"——模型应该以**当前对话意图为准**，而不是盲目用记忆偏好覆盖用户的明确指令。

这需要在 System Prompt 里明确说明：

```
【已知偏好】仅在用户未明确指定时使用。
当用户明确说出具体城市/货币时，以用户当前输入为准，不使用已知偏好。
```

## 五、复盘问题 3：多 Agent 什么时候值得引入

**问：Day 41 的 Planner/Executor/Critic 模式增加了 3 倍的 LLM 调用次数（每个角色一次）。什么类型的任务值得付出这个代价？**

**答**：引入多 Agent 的判断标准是**任务的"可分解性"和"容错需求"**：

**值得引入的场景**（满足任意一条）：
- 任务有明确的多个子步骤，且步骤之间有依赖关系（先查天气再决定带不带伞）
- 任务执行错误的代价高（如写邮件、生成报告），需要 Critic 把关
- 任务规模大，一个模型的上下文窗口放不下所有子任务的结果
- 不同步骤需要不同能力的模型（规划用推理强的模型，执行用速度快的模型）

**不值得引入的场景**：
- 简单的单工具调用（"查北京天气"）——Planner 拆出来也只有一个子任务，白白多两次 LLM 调用
- 对延迟敏感的实时对话——多 Agent 串行 3 次 LLM 调用，响应时间 3 倍以上
- 原型阶段——先跑通单 Agent，观察哪类任务确实规划不好，再针对性引入

**今天项目的建议**：默认用单 Agent（Day 25 的 ReAct），遇到"需要拆解子任务"的复合问题时，临时切换到 Planner/Executor/Critic 三角色——在 LangGraph 里可以通过条件边实现这个动态切换。

## 六、Agent 行为评估框架

### 6.1 测试 Case 的三元组结构

每条测试 case 包含三个字段：

```python
@dataclass
class AgentTestCase:
    case_id: str
    user_input: str                    # 用户输入
    expected_tool_calls: list[str]     # 预期工具调用序列（工具名列表，按顺序）
    expected_answer_points: list[str]  # 预期最终回答要点（模糊匹配关键词）
    category: str                      # 任务类型（single_tool / multi_step / boundary）
```

三元组的评估逻辑：

| 字段 | 验证什么 | 评分方式 |
|-----|---------|---------|
| `expected_tool_calls` | Agent 是否调用了正确的工具（工具触发准确率） | 精确匹配工具名序列（顺序也要对） |
| `expected_answer_points` | 最终回答是否包含关键信息（内容正确性） | 关键词模糊匹配（`any(kw in answer for kw in points)`） |

两者都通过才算整条 case 通过。工具调用对但回答错（工具返回了结果但模型没用上）和工具调用错但回答对（模型"瞎猜"出了正确答案）都要分别标记，帮助定位问题。

### 6.2 三类任务分类与评估维度

| 类型 | 含义 | 评估的能力 | 典型 Case |
|-----|------|----------|----------|
| **single_tool** | 单工具调用，一步到位 | 工具触发精准率（不多不少） | "北京今天天气？" |
| **multi_step** | 需要多步工具调用或任务拆解 | 规划能力 + 步骤依赖处理 | "帮我规划上海商务行，需要天气和汇率" |
| **boundary** | 边界情况：拒答 / 工具不存在 / 参数缺失 | 鲁棒性和边界识别 | "帮我查火星天气"（不支持的城市） |

通常哪类任务通过率最低：**multi_step**（Planner 容易漏拆子任务或顺序搞错）和 **boundary**（模型容易强行调工具而不是礼貌拒绝）。

### 6.3 示例评估报告（15 条 Case）

```python
TEST_CASES = [
    # ── single_tool（6 条）──
    AgentTestCase("s01", "北京今天天气怎么样？",
        ["get_weather"], ["北京", "°C"], "single_tool"),
    AgentTestCase("s02", "查一下上海天气",
        ["get_weather"], ["上海", "湿度"], "single_tool"),
    AgentTestCase("s03", "1 美元换多少人民币？",
        ["get_exchange_rate"], ["USD", "CNY", "7."], "single_tool"),
    AgentTestCase("s04", "欧元兑人民币汇率",
        ["get_exchange_rate"], ["EUR", "CNY"], "single_tool"),
    AgentTestCase("s05", "帮我记住我常用的城市是广州",
        ["save_preference"], ["广州", "记住"], "single_tool"),
    AgentTestCase("s06", "天气怎么样？",   # 无城市，应用已知偏好
        ["get_weather"], ["°C"], "single_tool"),

    # ── multi_step（6 条）──
    AgentTestCase("m01", "帮我规划去上海的商务行程，我需要知道天气和美元汇率",
        ["get_weather", "get_exchange_rate"], ["上海", "USD", "°C"], "multi_step"),
    AgentTestCase("m02", "我要去广州出差，先查天气，再查欧元兑人民币",
        ["get_weather", "get_exchange_rate"], ["广州", "EUR"], "multi_step"),
    AgentTestCase("m03", "同时告诉我北京和上海的天气",
        ["get_weather", "get_weather"], ["北京", "上海"], "multi_step"),
    AgentTestCase("m04", "查北京天气，如果下雨就提醒我带伞",
        ["get_weather"], ["北京"], "multi_step"),
    AgentTestCase("m05", "帮我记住货币是美元，然后查一下汇率",
        ["save_preference", "get_exchange_rate"], ["USD", "CNY"], "multi_step"),
    AgentTestCase("m06", "我去上海和广州各出差一天，各地天气如何",
        ["get_weather", "get_weather"], ["上海", "广州"], "multi_step"),

    # ── boundary（3 条）──
    AgentTestCase("b01", "帮我查火星的天气",
        [], ["不支持", "暂无"], "boundary"),       # 应该礼貌拒绝，不调工具
    AgentTestCase("b02", "比特币兑人民币汇率",
        [], ["不支持", "暂不"], "boundary"),        # 不支持的货币对
    AgentTestCase("b03", "你好，今天有什么可以帮你？",
        [], [], "boundary"),                        # 闲聊，不应触发任何工具
]
```

**评分示例（假设测试结果）**：

| Case ID | 类型 | 工具调用 ✓/✗ | 回答要点 ✓/✗ | 通过 |
|---------|------|------------|------------|-----|
| s01 | single | ✓ | ✓ | ✅ |
| s02 | single | ✓ | ✓ | ✅ |
| s03 | single | ✓ | ✓ | ✅ |
| s04 | single | ✓ | ✓ | ✅ |
| s05 | single | ✓ | ✓ | ✅ |
| s06 | single | ✓ | ✓ | ✅ |
| m01 | multi | ✓ | ✓ | ✅ |
| m02 | multi | ✓ | ✓ | ✅ |
| m03 | multi | ✗（只调了一次） | ✗ | ❌ |
| m04 | multi | ✓ | ✓ | ✅ |
| m05 | multi | ✗（顺序错了） | ✓ | ❌ |
| m06 | multi | ✗（只调了一次） | ✗ | ❌ |
| b01 | boundary | ✓（未触发） | ✗（没说"不支持"） | ❌ |
| b02 | boundary | ✓（未触发） | ✓ | ✅ |
| b03 | boundary | ✓（未触发） | ✓ | ✅ |

**汇总**：

| 类型 | 总数 | 通过 | 通过率 |
|-----|------|------|-------|
| single_tool | 6 | 6 | **100%** |
| multi_step | 6 | 3 | **50%** |
| boundary | 3 | 2 | **67%** |
| **总计** | **15** | **11** | **73%** |

**结论**：multi_step 通过率最低（50%），主要问题是"需要调用同一工具多次时只调一次"——下一步优化方向是改进 Planner 的拆解 Prompt，明确要求对同一工具的不同参数生成多个子任务。

### 6.4 通过率低时的根因定位

拿到通过率后，按"工具调用 ✗"和"回答要点 ✗"分别统计：

```
工具调用 ✗   → Prompt 问题（工具描述不清 / System Prompt 引导不足）或
              模型判断问题（该调没调 / 不该调硬调）
              → 先看工具的 description 够不够清晰

回答要点 ✗   → 工具结果没有被正确使用（模型读了结果但没组织进回答）
且工具调用 ✓   或工具返回了错误内容
              → 检查工具返回值格式、检查 ToolMessage 是否正确传递

两者都 ✗     → 通常是工具调用错了导致回答也错了，优先修工具调用
```
