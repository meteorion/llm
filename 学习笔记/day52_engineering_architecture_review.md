## 一、第 7–8 周产出回顾：Day 43–51 学了什么

Day 43–51 这九天的内容都在回答同一个问题："一个能跑的 Demo，要补齐哪些能力才算具备生产可维护性？"——顺序上先解决"看得见"，再解决"控成本"，最后解决"扛得住"：

```
Day 43–44（可观测性）：
  从"能跑"到"能被观测"——接入 LangFuse，把日志升级成可按 trace_id 关联的结构化记录

Day 45–47（成本与性能）：
  缓存省重复请求 → 批处理省单次固定开销 → 分级路由省"用错模型"的钱
  三者互不替代，分别针对不同的成本来源

Day 48–49（架构与并发风险）：
  模型网关统一多 Provider 接口 → 限流保护网关不被单一来源打爆

Day 50–51（上下文与状态）：
  上下文工程管好"这一次请求裝什么" → 状态管理管好"这个会话/任务重启后还在不在"
```

九天内容层层递进：先能看见问题（可观测性），再控制成本（缓存/批处理/路由），再统一入口并设防线（网关/限流），最后管好请求内部和跨请求之间的状态（上下文工程/状态管理）。

## 二、复盘问题一：这几样工程化能力分别解决了什么隐性成本

### 2.1 隐性成本分类框架

"隐性成本"指的是那些在 Demo 阶段不会暴露、但规模变大后会突然放大的代价。可以归纳成五类：

| 隐性成本类型 | 具体表现 |
|------------|---------|
| **切换成本** | 换一个模型 Provider、换一个部署环境时，需要改动的代码范围 |
| **并发风险** | 单一用户/来源的高频请求把系统资源（额度、并发数）耗尽，影响其他用户 |
| **单次开销** | 每次请求里，除了"真正有用的计算"之外浪费掉的固定成本（连接建立、重复前缀处理） |
| **上下文浪费** | 请求里塞进了模型用不上或用不好的信息，占用 Token 预算却没有提升回答质量 |
| **单点故障** | 状态只存在一个地方（一个进程、一个变量），这个地方失效后全部丢失或不可恢复 |

### 2.2 逐项拆解：五项能力对应的隐性成本

| 能力 | 对应 Day | 解决的隐性成本 | 不解决的问题 |
|-----|---------|--------------|------------|
| **模型网关** | 48 | 切换成本——不加网关时，换一个 Provider 要改所有调用点；网关把差异收拢到一层配置 | 网关本身不做限流、不做分级路由，那是另外两层的职责 |
| **限流** | 49 | 并发风险——不限流时，一个异常来源可以打满整个 Provider 配额或产生失控账单 | 限流不解决"用错模型浪费钱"的问题，那是分级路由的职责 |
| **批处理** | 46 | 单次开销——逐条调用时，每次请求都要重新走一遍连接建立、Prompt 前缀处理；批处理把固定开销摊薄 | 批处理不解决"重复问同一个问题"的浪费，那是缓存的职责 |
| **上下文工程** | 50 | 上下文浪费——不做分区管理时，历史消息、检索结果、工具返回随意堆叠，挤占了当前问题该有的 Token 预算 | 上下文工程不负责"这份检索结果本身准不准"，那是 RAG 优化（Day 58 起）的职责 |
| **状态管理** | 51 | 单点故障——会话/任务状态只存在进程内存时，进程一旦重启，所有进行中的会话和任务全部丢失 | 状态管理不负责"图内部一次执行的暂停恢复"，那是 Day 35 Checkpoint 的职责 |

**一句话总结这张表**：网关管"换谁"，限流管"谁在打谁"，批处理管"每次白花的钱"，上下文工程管"这次请求装了什么"，状态管理管"状态放在哪、丢不丢得起"——五个问题互不重叠，也互不能替代。

### 2.3 补充三项：可观测性 / 缓存 / 分级路由 各自对应什么隐性成本

复盘问题原文只点名了五项，但 Day 43–47 的三项内容同样是这周的产出，一并归类：

| 能力 | 对应 Day | 解决的隐性成本 |
|-----|---------|--------------|
| **可观测性（LangFuse）** | 43–44 | "不可观测成本"——出问题时无法定位是哪一次调用、哪一步耗时异常，只能靠猜；结构化 trace 把排查时间从"翻日志"降到"点开一条链路" |
| **缓存** | 45 | "重复计算成本"——完全相同或语义相近的请求被重复计算一遍，浪费的是本可以直接复用的结果 |
| **分级路由** | 47 | "模型选型成本"——简单任务用了昂贵的大模型，多付的差价随请求量线性累积 |

补上这三项后，Day 43–51 的九项内容正好覆盖了从"看不见问题"到"看得见但控不住成本"再到"控住成本但扛不住并发和重启"的完整链条。

## 三、复盘问题二：小规模项目还有必要做这些吗，边界在哪

### 3.1 判断信号：什么时候该引入

不是每个项目都要把九项能力做全，判断依据是**规模信号**而不是"看起来专业"：

| 信号 | 出现时该引入的能力 |
|-----|------------------|
| 出过一次"不知道哪次调用花了这么多钱/这么慢" | 可观测性（Day 43–44） |
| 同一个问题被不同用户反复问 | 缓存（Day 45） |
| 有明确的批量任务（如给 100 条数据打标签） | 批处理（Day 46） |
| 请求里有明显"简单 vs 复杂"的区分，且都在用同一个模型 | 分级路由（Day 47） |
| 计划接入第二个模型 Provider，或已经因为切 Provider 改了好几处代码 | 模型网关（Day 48） |
| 出现过一次异常来源把请求打满、或者担心成本失控 | 限流（Day 49） |
| 上下文里同时有历史/RAG/工具结果，且出现过"模型看漏了当前问题"的情况 | 上下文工程（Day 50） |
| 部署了不止一个实例，或者重启后用户抱怨"聊天记录没了" | 状态管理（Day 51） |

**没有出现对应信号之前，提前引入这些能力属于过度工程**——这正是 `plan.md` 里"常见误区 5：忽视成本与稳定性"的反面：不是所有工程化能力都该无脑叠加，只在信号出现时才是合理时机。

### 3.2 分级清单：无论规模都值得 vs 按需引入

| 分级 | 能力 | 理由 |
|-----|------|------|
| **无论规模都值得（成本极低，收益立现）** | 可观测性基础日志（trace_id/tokens/cost 字段） | 加一个字段的成本几乎为零，出问题时是唯一的排查依据 |
| | 上下文工程的"固定分区顺序"设计 | 不需要额外基础设施，只是组装 Prompt 时的顺序约定 |
| **按需引入（有信号才做）** | 缓存 | 请求有重复模式才有收益，单次性任务加缓存反而增加维护成本 |
| | 分级路由 | 只有一个模型可用、或任务复杂度单一时没有路由的意义 |
| | 批处理 | 没有批量场景时，为一次性请求引入并发调度是浪费 |
| | 模型网关 | 单 Provider、短期不会换模型时，网关是提前抽象 |
| | 限流 | 单用户内部工具、没有外部暴露风险时可以先不做 |
| | 状态管理外部化 | 单实例、可接受重启丢会话的内部 Demo，可以继续用 `gr.State` |

**边界判断口诀**：日志和上下文顺序设计"随手就该做"；缓存/路由/批处理/网关/限流/状态外部化"等信号出现再做"——把该做的和按需做的分开，才不会在小项目上花冤枉功夫，也不会在真正需要时漏掉关键能力。

## 五、工程化架构小结（本周产出物）

综合以上两个复盘问题，本周的产出物是这样一份"能力 — 隐性成本 — 引入阈值"对照小结：

```
可观测性   → 不可观测成本   → 阈值：几乎无阈值，越早接入越好
上下文工程 → 上下文浪费     → 阈值：几乎无阈值，只是设计约定
缓存       → 重复计算成本   → 阈值：出现重复请求模式
分级路由   → 模型选型成本   → 阈值：任务复杂度分层 + 请求量足够大到差价明显
批处理     → 单次开销       → 阈值：出现批量、非实时任务
模型网关   → 切换成本       → 阈值：接入第二个 Provider 或预期会切换
限流       → 并发风险       → 阈值：服务对外暴露，或曾经历成本/并发失控
状态管理   → 单点故障       → 阈值：多实例部署，或用户对"重启丢状态"零容忍
```

这份小结的价值不在于"记住九个名词"，而在于建立一个判断习惯：遇到新的工程化选项时，先问"它对应哪类隐性成本"和"我的项目现在有没有触发对应的信号"，而不是看到别人用了什么就照单全收。

## 六、下一步预告

Day 53 进入**Prompt 注入攻防**：本周解决的是"性能、成本、可维护性"三类工程问题，Day 53 起转向**安全**——区分直接注入和间接注入（工具返回内容夹带攻击指令），这是 Day 48 网关层和 Day 51 状态管理都还没有覆盖的风险面：网关统一了调用入口，但没有过滤"入口传进来的内容本身是否包含攻击指令"。这是走向生产部署前必须补上的最后一类隐性成本——安全风险。
