## 一、Prompt 优化的核心框架

### 1.1 四类优化手段总览

前十天已经零散接触过角色设定（Day 4）、任务约束（Day 5）、字段定义（Day 6）、Schema 约束（Day 8）、类别定义（Day 10），Day 11 把这些手段收敛成四个可复用的类别：

```
┌────────────────────────────────────────────────────────────────────┐
│                    Prompt 优化的四类手段                                │
├────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ① 角色设定（Role Setting）                                          │
│     "你是一位资深客服主管" —— 让模型代入特定视角和专业背景               │
│                                                                      │
│  ② 目标声明（Explicit Objective）                                    │
│     "你的任务是判断这条工单的紧急程度" —— 消除任务本身的歧义             │
│                                                                      │
│  ③ Few-shot 示例                                                     │
│     给 2-3 组"输入 → 期望输出"的示例 —— 用样例锚定判断标准               │
│                                                                      │
│  ④ 输出限制（Output Constraints）                                     │
│     格式、取值范围、长度 —— 让输出可解析、可复现                        │
│                                                                      │
│  四者不是互斥的，一个成熟的生产级 Prompt 通常同时用到全部四种           │
│                                                                      │
└────────────────────────────────────────────────────────────────────┘
```

### 1.2 为什么"写清楚"比"写聪明"更重要

很多人优化 Prompt 的第一反应是加"魔法词"（"请仔细思考"、"你是世界上最好的专家"），但真正影响输出质量的，是**任务本身有没有被讲清楚**：

```
┌───────────────────────────────────────────────────────────────────┐
│              "写聪明" vs "写清楚"                                     │
├───────────────────────────────────────────────────────────────────┤
│                                                                     │
│  写聪明（效果有限甚至无效）：                                          │
│  "你是全宇宙最专业的客服专家，请务必认真仔细地分析这条反馈"              │
│  —— 堆砌形容词不会让模型"更努力思考"，模型没有"偷懒"这个状态             │
│                                                                     │
│  写清楚（真正有效）：                                                  │
│  "紧急程度的判断标准：涉及资金损失或安全问题 = 5，              │
│  影响正常使用但有替代方案 = 3，纯咨询无影响 = 1"                        │
│  —— 把隐藏在人脑子里的判断标准显式写出来，模型才能对齐这个标准           │
│                                                                     │
└───────────────────────────────────────────────────────────────────┘
```

**核心结论**：Prompt 优化的本质不是"讨好模型"，而是**把任务定义中原本模糊、依赖常识和经验的部分，用文字显式表达出来**。四类优化手段本质上都是"消除歧义"的不同角度：角色设定消除"用什么标准判断"的歧义，目标声明消除"要做什么"的歧义，Few-shot 消除"边界案例怎么判断"的歧义，输出限制消除"结果长什么样"的歧义。

### 1.3 真优化 vs 假优化：如何辨别过拟合测试集

```
┌──────────────────────────────────────────────────────────────────────┐
│            "Prompt 变好了" 还是 "恰好蒙对了这几条测试数据"？             │
├──────────────────────────────────────────────────────────────────────┤
│                                                                        │
│  陷阱场景：                                                            │
│  用 5 条测试数据反复调 Prompt，直到这 5 条全部正确 → 误以为优化成功       │
│                                                                        │
│  问题：这 5 条数据的措辞、边界情况可能被"针对性"覆盖了，                  │
│  换一批新数据，准确率可能骤降 —— 这叫对测试集"过拟合"                    │
│                                                                        │
│  正确做法：                                                            │
│  1. 测试集要有一定规模（至少 15-20 条）且覆盖不同难度                    │
│  2. 优化过程中的数据（开发集）和最终验证的数据（留出集）要分开            │
│  3. 只在开发集上迭代 Prompt，留出集只在"定稿"后跑一次，                  │
│     留出集的结果才是真实预期表现                                       │
│                                                                        │
└──────────────────────────────────────────────────────────────────────┘
```

## 二、四类优化手段逐个拆解

### 2.1 角色设定（Role Setting）

角色设定通过 `system` 消息告诉模型"以什么身份、什么专业标准"完成任务，本质是给模型提供一个隐含的知识和判断视角：

```python
# 无角色设定
{"role": "user", "content": "这条客服反馈应该打几分紧急程度？"}

# 有角色设定
{"role": "system", "content": "你是一名有 5 年经验的电商客服主管，擅长根据历史工单经验判断问题的紧急程度和处理优先级。"}
{"role": "user", "content": "这条客服反馈应该打几分紧急程度？"}
```

角色设定对**主观性较强、依赖领域经验**的任务效果明显（如"这段代码有没有安全隐患"要设定"资深安全工程师"角色）；对**客观性强、判断标准已经在 Prompt 里写清楚**的任务（如严格按 Schema 抽取字段）收益有限——这时候角色设定不是决定因素，字段定义是否清晰才是。

### 2.2 目标声明（Explicit Objective）

目标声明是用一句话明确"这次调用到底要模型做什么"，避免任务本身有多种理解方式：

```
┌───────────────────────────────────────────────────────────────┐
│                  目标声明消除歧义的例子                              │
├───────────────────────────────────────────────────────────────┤
│                                                                 │
│  模糊："看看这条反馈"                                              │
│  → 模型不知道是要"总结内容"还是"判断情绪"还是"打紧急程度分"           │
│                                                                 │
│  明确："你的任务是：仅判断这条反馈的紧急程度（1-5 分），                │
│  不需要总结内容、不需要给处理建议"                                    │
│  → 排除了模型"顺便多做点什么"的可能性                                │
│                                                                 │
└───────────────────────────────────────────────────────────────┘
```

一个常见的误区是把"目标"和"输出格式"混在一起说，导致 Prompt 读起来任务不清晰。建议目标声明单独一段，格式约束放在后面单独一段，各自职责分明。

### 2.3 Few-shot 示例

Few-shot 通过给出"输入 → 期望输出"的具体样例，让模型从示例中归纳判断标准，尤其适合**边界案例难以用文字穷举**的场景：

```python
few_shot_examples = """
示例 1：
反馈："账户里的 5000 元被扣了两次，联系不上客服" → 紧急程度：5（涉及资金损失）
示例 2：
反馈："APP 打开有点慢，但还能正常用" → 紧急程度：2（影响体验，不影响功能）
示例 3：
反馈："请问会员什么时候能续费打折" → 紧急程度：1（纯咨询）
"""
```

```
┌────────────────────────────────────────────────────────────────┐
│              文字规则 vs Few-shot 示例：互补而非替代                  │
├────────────────────────────────────────────────────────────────┤
│                                                                  │
│  文字规则擅长：明确的、可枚举的判断标准                                │
│  "涉及资金损失 = 5 分"                                             │
│                                                                  │
│  Few-shot 擅长：难以用规则穷举的"感觉"，靠类比而非规则判断              │
│  "这条反馈的语气和示例 2 很像，都是体验层面的小问题，应该打 2 分"        │
│                                                                  │
│  最佳实践：先写清楚的文字规则覆盖大多数情况，                          │
│  再补 2-3 个 Few-shot 示例覆盖规则难以描述的边界情况                  │
│                                                                  │
└────────────────────────────────────────────────────────────────┘
```

注意 Few-shot 示例数量并非越多越好——示例太多会占用大量 Token（增加成本），且示例本身如果覆盖不均衡（比如 3 个示例都是高分工单），反而会让模型产生偏向性。通常 2-4 个、覆盖不同分值/类别区间的示例效果最好。

### 2.4 输出限制（Output Constraints）

输出限制是 Day 5（长度）、Day 8（Schema）、Day 10（enum）里反复出现的手段，Day 11 把它们统一看作"消除输出形态歧义"的工具：

```python
output_constraint = (
    "只输出 JSON：{\"urgency\": <1到5的整数>}，"
    "不要输出解释、不要输出 markdown 代码块。"
)
```

| 约束类型 | 解决的歧义 | 对应 Day |
|---------|-----------|---------|
| 长度约束 | 输出该有多长 | Day 5 |
| JSON Schema / Pydantic | 字段名、类型该是什么 | Day 8 |
| enum | 取值范围该是什么 | Day 10 |
| 格式声明（"只输出 JSON"） | 输出里能不能有多余文字 | Day 6/9 |

### 3.2 V1/V2/V3 三个版本的设计思路

```python
def prompt_v1(text: str) -> str:
    """V1：极简版 —— 只有目标声明和输出限制，没有判断标准，没有角色，没有示例"""
    return (
        f"判断以下客服反馈的紧急程度，用 1-5 的整数打分。"
        f"只输出 JSON：{{\"urgency\": <整数>}}\n\n反馈：{text}"
    )


def prompt_v2(text: str) -> str:
    """V2：加角色设定 + 明确的文字判断标准"""
    return (
        "你是一名有 5 年经验的电商客服主管，擅长判断工单的紧急程度。\n"
        "判断标准：\n"
        "5 分：涉及资金损失、安全问题，或用户明确表示紧急\n"
        "4 分：影响正常使用，且用户明确表达了时间压力\n"
        "3 分：影响使用但有替代方案，或问题描述模糊\n"
        "2 分：轻微影响体验，不影响核心功能\n"
        "1 分：纯咨询，无负面体验\n\n"
        f"只输出 JSON：{{\"urgency\": <1到5的整数>}}，不要输出解释。\n\n反馈：{text}"
    )


def prompt_v3(text: str) -> str:
    """V3：在 V2 基础上补充 Few-shot 示例，覆盖判断标准较难穷举的边界情况"""
    examples = (
        "示例：\n"
        "反馈：\"账户里的 5000 元被扣了两次，联系不上客服\" → {\"urgency\": 5}\n"
        "反馈：\"APP 打开有点慢，但还能正常用\" → {\"urgency\": 2}\n"
        "反馈：\"请问会员什么时候能续费打折\" → {\"urgency\": 1}\n\n"
    )
    return prompt_v2(text).replace("只输出 JSON", examples + "只输出 JSON")
```

三个版本的差异是**递进式**的：V1 只有最基础的目标+格式约束（对照组），V2 加上角色设定和文字判断标准，V3 在 V2 基础上再加 Few-shot——这样设计便于观察"每加一类手段，效果提升了多少"，而不是三个版本互相独立、无法归因差异来源。

### 3.3 对比实验框架实现

```python
def run_prompt(prompt_fn, text: str) -> int:
    response = client.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt_fn(text)}],
        temperature=0.0,
        response_format={"type": "json_object"},
    )
    data = json.loads(response.choices[0].message.content)
    return data.get("urgency")


def evaluate_prompt(prompt_fn, test_set: list[dict], n_runs: int = 3) -> dict:
    """对每条测试数据跑 n_runs 次，同时统计准确率（vs expected）和稳定性（多次结果是否一致）"""
    per_item_results = []

    for item in test_set:
        runs = [run_prompt(prompt_fn, item["text"]) for _ in range(n_runs)]
        most_common = max(set(runs), key=runs.count)
        is_stable = len(set(runs)) == 1
        is_correct = most_common == item["expected"]
        per_item_results.append({
            "text": item["text"], "expected": item["expected"],
            "runs": runs, "stable": is_stable, "correct": is_correct,
        })

    accuracy = sum(r["correct"] for r in per_item_results) / len(per_item_results)
    stability = sum(r["stable"] for r in per_item_results) / len(per_item_results)
    return {"accuracy": accuracy, "stability": stability, "details": per_item_results}


def compare_prompts(prompts: dict, test_set: list[dict], n_runs: int = 3):
    for name, fn in prompts.items():
        result = evaluate_prompt(fn, test_set, n_runs)
        print(f"{name}：准确率 {result['accuracy']:.0%}，稳定性 {result['stability']:.0%}")
```

`n_runs` 参数是关键——每条数据跑多次（`temperature=0` 理论上应该完全稳定，但实践中 API 偶尔仍有微小随机性），用多数投票得到最终答案算准确率，同时用"是否每次结果都一样"衡量稳定性，这样**准确率和稳定性是两个独立的、都能量化的指标**，而不是凭感觉判断"这个 Prompt 看起来更好"。

## 四、稳定性与准确率的关系与权衡

### 4.1 两个独立的评估维度

```
┌──────────────────────────────────────────────────────────────────┐
│                准确率（Accuracy） vs 稳定性（Stability）              │
├──────────────────────────────────────────────────────────────────┤
│                                                                    │
│  准确率：模型输出和"人工标注的正确答案"的一致程度                       │
│  衡量方式：多数投票结果 == expected 的比例                            │
│                                                                    │
│  稳定性：同一条输入多次调用，结果是否一致                              │
│  衡量方式：多次运行结果完全相同的比例                                  │
│                                                                    │
│  两者不是一回事：一个 Prompt 可能"稳定地错"（每次都打错分，但每次        │
│  打的都一样），也可能"偶尔蒙对"（多次结果不一致，但多数投票恰好对）      │
│                                                                    │
└──────────────────────────────────────────────────────────────────┘
```

### 4.2 四象限：稳定性 × 准确率

```
                    高准确率            低准确率
              ┌──────────────────┬──────────────────┐
   高稳定性    │   理想状态          │   稳定地错          │
              │   可直接上线        │   判断标准本身有偏差  │
              │                    │   需要重新设计规则    │
              ├──────────────────┼──────────────────┤
   低稳定性    │   多数投票能救       │   最差情况          │
              │   但单次调用不可靠    │   Prompt 设计本身   │
              │   建议提高约束强度    │   存在根本性歧义     │
              └──────────────────┴──────────────────┘
```

三个版本的典型实验结果分布（8 条测试数据，每条跑 3 次）：

```
V1_极简：准确率 50%，稳定性 62%   ← 落在"低稳定性/低准确率"象限
V2_角色+规则：准确率 75%，稳定性 88%   ← 明显改善，接近"理想状态"
V3_角色+规则+示例：准确率 88%，稳定性 100%   ← 边界案例（如"物流没更新，急用"）判断也对齐了
```

**结论**：V1 缺乏判断标准时，模型对"3 分 vs 4 分"这类边界打分本身就没有稳定依据，同一条数据不同次调用给出不同分数；V2 的文字规则大幅提升了稳定性和准确率；V3 的 Few-shot 示例进一步锚定了规则难以覆盖的边界案例（如"物流未更新但用户表达了急用"这种混合信号）。

### 4.3 用留出集合验证，避免"过拟合"测试数据

```python
DEV_SET = TEST_SET[:5]     # 开发集：用于迭代 Prompt V1 → V2 → V3
HOLDOUT_SET = TEST_SET[5:] # 留出集：只在 Prompt 定稿后跑一次，验证真实表现

# 迭代阶段：只看 DEV_SET 上的表现调整 Prompt
compare_prompts({"V1": prompt_v1, "V2": prompt_v2, "V3": prompt_v3}, DEV_SET)

# 定稿阶段：用从未参与过调优的 HOLDOUT_SET 验证最终版本
final_result = evaluate_prompt(prompt_v3, HOLDOUT_SET, n_runs=3)
print(f"留出集验证：准确率 {final_result['accuracy']:.0%}")
```

如果留出集上的准确率和开发集差距很大（比如开发集 90%，留出集只有 60%），说明前面的"优化"很可能是针对开发集里几条数据的措辞做了过度适配，而不是真正抓住了任务的通用判断标准，需要回头检查 Prompt 里是否有"恰好覆盖了某几条测试数据用词"的痕迹。

## 六、Day 11 知识速查

### 四类优化手段速查

| 手段 | 解决的歧义 | 适用场景 |
|------|-----------|---------|
| 角色设定 | 用什么标准/视角判断 | 主观性强、依赖领域经验的任务 |
| 目标声明 | 要做什么 | 任务本身容易有多种理解 |
| Few-shot 示例 | 边界案例怎么判断 | 规则难以用文字穷举的场景 |
| 输出限制 | 结果长什么样 | 所有需要程序解析输出的场景 |

### 评估维度速查

| 维度 | 定义 | 衡量方式 |
|------|------|---------|
| 准确率 | 输出与人工标注答案的一致程度 | 多数投票结果 == expected 的比例 |
| 稳定性 | 同一输入多次调用结果是否一致 | 多次运行结果完全相同的比例 |

**Day 12：建立成本意识**

Day 11 关注的是"输出质量"，Day 12 会把视角切换到"输出质量之外的另一个约束"——成本：
