## 一、第 9 周（路线 C 全程）产出回顾：Day 43–56 学了什么

Day 43–56 沿着 Day 52 复盘时总结的四阶段推进：可观测性 → 成本与性能 → 架构与并发 → 安全与部署：

```
Day 43–44（可观测性）：接入 LangFuse，日志升级为可按 trace_id 关联的结构化记录
Day 45–47（成本与性能）：缓存省重复请求，批处理省单次固定开销，分级路由省模型选型成本
Day 48–49（架构与并发风险）：模型网关统一多 Provider 接口，限流保护网关不被打爆
Day 50–51（上下文与状态）：上下文工程管好单次请求装什么，状态管理管好跨请求状态存哪
Day 52（复盘）：五项能力对应的隐性成本框架 + 规模信号判断标准
Day 53–54（安全）：Prompt 注入攻防（直接/间接注入四层防御）+ 输出护栏（Guardrails 通用拦截层）
Day 55（反馈闭环）：反馈追踪采集用户满意度信号，回流到评估集和 Prompt 迭代
Day 56（部署）：Docker 容器化 + GitHub Actions CI + 向量库迁移到可远程访问的 Qdrant
```

这十四天覆盖了 `plan.md` 第三阶段"大模型工程化架构"提到的四块内容中的三块（工程化架构、成本与性能、安全），加上可观测性、评估回流、部署三项配套能力——路线 C 到今天为止已经覆盖完整。

## 二、Day 42 升级版项目的短板与本阶段整合方案

### 2.1 Day 42 项目遗留的短板

Day 42 的升级版 Agent（MCP 工具 + 长期记忆 + 多 Agent 协作 + LangGraph 编排）解决了"能力"层面的问题（工具复用、跨会话记忆、任务规划、流程可观测），但完全没有涉及"生产可维护性"层面：

| 短板 | 表现 |
|-----|------|
| **不可观测执行细节** | 只能靠 print 调试，出问题后无法定位具体是哪次调用的哪一步 |
| **成本不可控** | 没有缓存、没有分级路由、没有批处理，重复请求和简单任务都在用同一个（可能是昂贵的）模型 |
| **无并发防护** | 没有限流，单一来源可以无限制发起请求，成本和资源都可能被打爆 |
| **多 Provider 切换成本高** | 直接在业务代码里写死了模型调用方式，换 Provider 要改很多处 |
| **上下文管理粗放** | 历史消息、记忆、工具结果没有固定的分区和裁剪策略，容易出现"重要信息被挤出窗口" |
| **状态只在进程内存** | 会话/任务状态用的是内存变量，重启即丢失，无法多实例部署 |
| **无安全防护** | 没有对注入攻击做防御，也没有输出前的护栏校验 |
| **没有反馈闭环** | 不知道用户对回答的真实满意度，无法定向改进 |
| **无法公开访问** | 只能在本地运行，没有部署，没有 CI 质量门控 |

## 三、复盘问题：现在这个项目距离"能接真实用户流量"还差什么

### 3.1 已经具备的能力盘点

按 `plan.md` 第三阶段通关标准逐条对照：

```
✅ 能做出一个会自主判断并调用工具、可观察、可复现的 Agent（Day 33-42）
✅ 项目具备工程可维护性：配置外置、日志、重试、成本可控（Day 43-51）
✅ 能识别并缓解基本的安全风险，如 Prompt 注入（Day 53-54）
✅ 有公开可访问的部署形态 + CI 质量门控（Day 56）
```

### 3.2 仍然缺失的能力

即使十一项能力都整合完成，距离"真正对外承接生产流量"依然有几类没有覆盖到的问题——这些不属于本阶段范围，但值得明确列出，避免误以为"做完这些就万事俱备"：

| 缺失项 | 为什么重要 | 本路线覆盖情况 |
|-------|-----------|--------------|
| 用户身份认证与授权 | 目前的限流按用户 ID/IP 做区分，但没有真正的登录鉴权体系 | 未覆盖，需要额外接入（如 OAuth/JWT） |
| 多租户数据隔离 | 如果服务多个客户，需要保证租户之间数据/配置互不可见 | 未覆盖 |
| 灰度发布 / 回滚机制 | Day 56 的 CI 只做到"测试通过"，没有做到"新版本先给小流量验证" | 未覆盖，需要额外的发布策略 |
| SLA 监控与告警 | Day 43 的可观测性能"查询"调用链，但没有"超过阈值自动告警"的主动监控 | 部分覆盖（有数据基础，缺告警规则） |
| 容灾与高可用 | 单个 Qdrant/网关实例挂了怎么办，目前没有做冗余部署 | 未覆盖 |
| RAG 检索质量 | 目前的 RAG 系统还是 Day 15-20 的基础版本，检索准确率没有专门优化过 | 未覆盖，对应接下来的路线 B（Day 58-67） |

### 3.3 判断标准：什么规模的真实流量才需要补齐剩余项

和 Day 52 的"规模信号"判断逻辑一致——不是所有缺失项都要立刻补齐：

```
个人项目/小范围内测（几十到几百用户）：
  → 当前十一项能力已经足够支撑，缺失项可以先不做

对外提供付费服务、涉及多个客户：
  → 必须补齐身份认证、多租户隔离

有明确的可用性承诺（SLA）：
  → 必须补齐监控告警、容灾高可用、灰度发布

依赖检索准确率的业务场景（如知识库客服）：
  → 需要接下来的路线 B（RAG 优化）进一步打磨
```

## 四、生产就绪度检查清单

参照 Day 42 用测试 case 量化 Agent 行为的思路，这里用一份**能力维度检查清单**量化"生产就绪度"，而不是逐条功能测试：

```python
# readiness/checklist.py
from dataclasses import dataclass

@dataclass
class ReadinessItem:
    dimension: str       # 能力维度
    item: str            # 具体检查项
    status: bool         # 是否已具备
    note: str = ""

CHECKLIST = [
    ReadinessItem("可观测性", "每次请求可通过 trace_id 查到完整调用链", True),
    ReadinessItem("可观测性", "有结构化日志（trace_id/tokens/cost/latency）", True),
    ReadinessItem("成本控制", "高频重复请求命中缓存", True),
    ReadinessItem("成本控制", "简单任务自动路由到小模型", True),
    ReadinessItem("架构", "换模型 Provider 只改网关层配置", True),
    ReadinessItem("并发防护", "超额请求被限流正确拒绝", True),
    ReadinessItem("上下文管理", "上下文分区有固定顺序和裁剪规则", True),
    ReadinessItem("状态管理", "服务重启后会话/任务状态可恢复", True),
    ReadinessItem("安全", "红队测试的越狱/间接注入类用例被拦截", True),
    ReadinessItem("安全", "PII/越权/格式类违规输出被护栏拦截", True),
    ReadinessItem("反馈闭环", "低分回答可通过 trace_id 追溯并回流分析", True),
    ReadinessItem("部署", "有公开可访问 URL + CI 自动测试", True),
    ReadinessItem("部署", "向量库为可远程访问的存储，非本地文件", True),
    ReadinessItem("身份认证", "有真实的用户登录鉴权体系", False, "超出本路线范围，按需接入"),
    ReadinessItem("高可用", "关键组件（网关/向量库）有冗余部署", False, "单实例，无容灾"),
    ReadinessItem("发布策略", "新版本上线前有灰度验证机制", False, "目前是全量直接部署"),
]

def print_readiness_report(checklist: list[ReadinessItem]):
    passed = sum(1 for c in checklist if c.status)
    print(f"生产就绪度：{passed}/{len(checklist)} 项已具备\n")
    for c in checklist:
        mark = "✅" if c.status else "❌"
        suffix = f"（{c.note}）" if c.note else ""
        print(f"  {mark} [{c.dimension}] {c.item}{suffix}")
```

预期输出：

```
生产就绪度：13/16 项已具备

  ✅ [可观测性] 每次请求可通过 trace_id 查到完整调用链
  ✅ [可观测性] 有结构化日志（trace_id/tokens/cost/latency）
  ✅ [成本控制] 高频重复请求命中缓存
  ✅ [成本控制] 简单任务自动路由到小模型
  ✅ [架构] 换模型 Provider 只改网关层配置
  ✅ [并发防护] 超额请求被限流正确拒绝
  ✅ [上下文管理] 上下文分区有固定顺序和裁剪规则
  ✅ [状态管理] 服务重启后会话/任务状态可恢复
  ✅ [安全] 红队测试的越狱/间接注入类用例被拦截
  ✅ [安全] PII/越权/格式类违规输出被护栏拦截
  ✅ [反馈闭环] 低分回答可通过 trace_id 追溯并回流分析
  ✅ [部署] 有公开可访问 URL + CI 自动测试
  ✅ [部署] 向量库为可远程访问的存储，非本地文件
  ❌ [身份认证] 有真实的用户登录鉴权体系（超出本路线范围，按需接入）
  ❌ [高可用] 关键组件（网关/向量库）有冗余部署（单实例，无容灾）
  ❌ [发布策略] 新版本上线前有灰度验证机制（目前是全量直接部署）
```

**这份清单的价值**：13/16 已经覆盖了"个人项目/小范围内测"场景的全部需求，剩下 3 项只有在流量规模、业务承诺真正需要时才补——这正是 3.3 节判断标准的可执行版本。
