## 一、为什么 README 是项目的"脸"

### 1.1 5 分钟测试：陌生人能跑起来吗？

项目 README 的黄金标准只有一个：**一个从未见过这个项目的开发者，能在 5 分钟内把它跑起来吗？**

| 时间点 | 操作 |
|-------|------|
| 00:00 | 打开 README |
| 00:30 | 理解"这个项目是干什么的" |
| 01:00 | 找到环境要求（Python 版本、依赖） |
| 01:30 | git clone + pip install |
| 03:00 | 配置 .env（照着 .env.example） |
| 04:30 | python app.py |
| 05:00 | 看到界面，发第一条消息 |

如果任何一步超时、卡住或报不明原因的错误 → README 不合格。

**验证方法**：找一位没参与这个项目的朋友，看他能否在 5 分钟内跑起来；或者自己清空环境重新按 README 操作一遍。

### 1.2 README 必须包含的四个部分

| 部分 | 作用 |
|-----|------|
| 1. 项目介绍 | 30 秒内让读者知道这是什么 |
| 2. 功能列表 | 具体说能做什么（不是"智能助手"这种废话） |
| 3. 快速开始 | 安装 → 配置 → 运行，3 步内 |
| 4. 示例 | 真实的输入/输出截图或文字，胜过千字描述 |

可选但加分的部分：技术架构图、FAQ、部署说明、贡献指南。

### 1.3 常见疏漏：让人跑不起来的五种情况

| 疏漏 | 典型表现 | 修复方式 |
|-----|---------|---------|
| 缺少 Python 版本要求 | 用户 Python 3.8，代码用了 3.10 特性 | 在 README 顶部写 `Python 3.10+` |
| 缺 .env.example | 用户不知道需要配什么变量 | 提供 `.env.example`，注释每个变量的用途 |
| 依赖版本未锁定 | pip install 装了不兼容版本 | `requirements.txt` 中锁定关键依赖版本号 |
| 没说运行入口 | 用户不知道运行哪个文件 | 明确写 `python app.py` 或 `gradio app.py` |
| 示例不真实 | 截图是 PS 的，或描述与实际不符 | 按 README 步骤重新跑一遍，用真实截图 |

## 二、写好项目介绍

### 2.1 一句话介绍：用"做什么 + 怎么做到"结构

一句话介绍不是名词堆砌，而是让陌生人立刻理解**这个工具解决了什么问题**：

- ❌ 差的一句话："基于 LLM 的智能助手，支持多轮对话和工具调用"（"智能助手"没有边界，"工具调用"是实现细节不是用户价值）
- ✅ 好的一句话："一个可以帮你查实时天气、汇率的聊天助手——输入自然语言，自动调用对应工具并给出完整回答"

结构：**[用户能感知的功能] + [实现方式的关键差异化]**

### 2.2 功能列表：具体而非抽象

❌ 抽象（没有信息量）：

- 支持多种工具调用
- 智能对话
- 友好界面

✅ 具体（读者知道能用它做什么）：

- **天气查询**：输入"北京今天天气"，自动获取实时温度、天气状况
- **汇率换算**：输入"100 美元换多少人民币"，返回实时汇率和换算结果
- **多步推理**：同时询问天气和汇率，自动串行调用两个工具后汇总回答
- **工具链可视化**：界面右侧实时展示工具调用过程（工具名、参数、耗时）
- **多轮对话**：支持追问，记忆本轮对话上下文

### 2.3 技术栈说明：让读者快速定位自己的熟悉度

| 组件 | 技术选型 | 说明 |
|-----|---------|------|
| LLM | DeepSeek Chat | 通过 OpenAI 兼容 API 调用 |
| 界面 | Gradio 4.x | `gr.Blocks` 双栏布局 |
| 工具调用 | OpenAI Function Calling | JSON Schema 定义工具 |
| 配置管理 | python-dotenv | `.env` 文件 + `dataclass` 封装 |
| 运行环境 | Python 3.10+ | 无需 GPU |

## 三、写好运行步骤

### 3.1 三步启动原则

快速开始章节应该是**三步以内**的可执行命令序列，让用户无需思考：

```bash
# Step 1：克隆并安装
git clone https://github.com/your-name/your-project.git
cd your-project
pip install -r requirements.txt

# Step 2：配置 API Key
cp .env.example .env
# 然后编辑 .env，填入你的 DEEPSEEK_API_KEY

# Step 3：启动
python app.py
# 打开浏览器访问 http://127.0.0.1:7860
```

**三步之所以是上限**：如果步骤超过三步，说明工程化不够（缺少自动化）或文档不够精简。超过三步应该考虑写成脚本或 Makefile。

### 3.2 每步都必须可验证

每步操作后都应该告诉用户**正确的结果是什么**，让用户能自检。在 README 里每步后加 ✅ 预期输出说明：

**Step 1：安装依赖**

```bash
pip install -r requirements.txt
```

✅ 预期：`Successfully installed` 若干包，无红色报错

**Step 2：配置**

```bash
cp .env.example .env
```

然后打开 `.env`，将 `your-api-key-here` 替换为你的 DeepSeek API Key。

✅ 预期：`.env` 文件中 `DEEPSEEK_API_KEY=sk-xxxxx`（非空）

**Step 3：运行**

```bash
python app.py
```

✅ 预期：终端输出 `Running on local URL: http://127.0.0.1:7860`，浏览器打开此地址可看到界面

### 3.3 .env 配置的正确写法

`.env.example` 文件是用户配置的向导，每个变量都要有注释：

```bash
# .env.example

# DeepSeek API Key（必填）
# 获取地址：https://platform.deepseek.com
DEEPSEEK_API_KEY=your-api-key-here

# 使用的模型（可选，默认 deepseek-chat）
MODEL=deepseek-chat

# API 基础 URL（可选，默认 DeepSeek 官方地址）
BASE_URL=https://api.deepseek.com/v1

# 工作流最大迭代次数，防止无限循环（可选，默认 6）
MAX_ITERATIONS=6

# 模型温度，0=最稳定，1=最有创意（可选，默认 0）
TEMPERATURE=0
```

`.gitignore` 中确保 `.env` 被忽略：

```gitignore
.env
__pycache__/
*.pyc
.idea/
.vscode/
```

## 四、写好示例输入输出

### 4.1 为什么示例比功能描述更有力

- **功能描述（抽象）**："支持实时天气查询和货币换算，可处理复合问题"
- **示例（具体）**：用户发"上海明天适合出门吗？顺便帮我算一下 500 欧元换多少人民币"，系统自动调用 get_weather 和 get_exchange_rate，回答"上海明天多云，22–28°C，适合出门。另外，500 欧元约等于 3,920 人民币（1 EUR = 7.84 CNY）"

示例让读者立刻知道：系统能处理复合问题（两个工具串行调用）、回答是自然语言、工具调用是自动推断的，用户不需要指定。

### 4.2 选择哪些示例：三类必选场景

| 类型 | 示例内容 | 展示的能力 |
|-----|---------|----------|
| **核心功能** | 单工具调用（天气 or 汇率） | 最基本功能正常工作 |
| **差异化亮点** | 多工具串行调用 + 工具链可视化截图 | 项目最有特色的能力 |
| **边界处理** | 不需要工具的普通聊天 | 系统足够"聪明"，不会滥用工具 |

可选加分：展示一个工具返回错误时模型的优雅处理（"暂不支持该城市"而非程序崩溃）。

### 4.3 示例的呈现格式

在 README 中用独立代码块呈现每段对话，用 `用户：` / `助手：` 前缀区分角色：

**示例 1：查询天气**

```
用户：北京今天天气怎么样？
助手：北京今天晴，气温 15–26°C，空气质量良好，适合户外活动。
```

**示例 2：换算汇率**

```
用户：100 美元能换多少人民币？
助手：当前汇率 1 USD = 7.24 CNY，100 美元约等于 724 元人民币。
```

**示例 3：复合问题（自动调用两个工具）**

```
用户：上海天气和今日欧元汇率都告诉我
     [工具调用链：get_weather("上海") → get_exchange_rate("EUR","CNY")]
助手：上海今天阴，气温 18–24°C，有小雨，建议带伞。
     欧元兑人民币今日汇率：1 EUR = 7.84 CNY。
```

**第二阶段（Day 15–21）：RAG 核心架构**

核心产出：Day 16 多格式文档加载器、Day 17 文本切分策略、Day 18 Embedding + 向量检索、Day 20 带引用溯源的完整 RAG 系统

核心技能：Tool Calling、Agent 循环、Gradio UI、工程化

### 6.2 最重要的五个认知转变

**1. "API 调用" → "工程系统"**

- 起点：把 API Key 填进去，发消息，收回复
- 终点：LLM 是系统中的一个组件，需要配置管理、异常处理、日志监控、成本控制，才能稳定运行

**2. "Prompt = 咒语" → "Prompt = 工程规格"**

- 起点：Prompt 写得越华丽越好，加更多修饰词
- 终点：Prompt 是给模型的规格说明——明确输入格式、输出格式、边界条件，和代码注释一样需要精简和迭代

**3. "模型什么都知道" → "RAG 补充实时知识"**

- 起点：大模型训练数据很多，直接问就好
- 终点：模型有知识截止日期，私有知识（公司文档）模型不知道；RAG = 先检索相关段落，再让模型基于段落回答

**4. "工具调用 = 插件" → "工具 = 能力扩展边界"**

- 起点：工具是一个附加功能
- 终点：工具定义了模型能做什么（查询、计算、存储、API 调用）；工具 description 的精确程度决定模型是否能在正确时机使用它

**5. "跑起来就行" → "可维护性是第一生产力"**

- 起点：Demo 能跑就算完成
- 终点：fail-fast 配置验证、分层异常处理、请求日志、测试记录——这些"非功能需求"决定了项目能否被他人运行和维护

### 6.3 下一步去哪里

**路线 A：深化 Agent 能力（路线图第四阶段方向）**

- LangGraph：用图结构定义复杂 Agent 流程（分支、循环、多 Agent 协作）
- MCP（Model Context Protocol）：标准化工具接口协议
- Memory 组件：跨对话的长期记忆（向量存储 + 摘要压缩）
- 多 Agent 系统：Planner + Executor + Critic 角色分工

**路线 B：提升 RAG 系统质量**

- 多路召回（向量检索 + BM25 关键词检索 + 知识图谱）
- Reranker（Cross-Encoder 重排序提升精度）
- HyDE（Hypothetical Document Embeddings 改善检索）
- RAGAS 评估框架（自动化 RAG 质量测量）

**路线 C：走向生产部署**

- 可观测性：LangFuse / LangSmith 追踪每次 LLM 调用
- 成本控制：Prompt 缓存、模型分级路由、批处理
- 安全：Prompt 注入防护、输出护栏、内容过滤
- 部署：Docker 容器化、Hugging Face Spaces 托管

**判断选哪条路线**：做完 30 天后，回顾 Day 27–29 的项目，看**哪个部分让你最不满意**——那就是下一阶段的重点。

这三条路线已经具体化为可执行的日常任务清单：见 [`day31_67_deepening_roadmap.md`](../规划文档/day31_67_deepening_roadmap.md)（Day 31–67，先补 LangChain/LangGraph 框架基础，再按 A→C→B 顺序系统覆盖）。

## 九、30 天学习结束语
