## 一、第 11 周产出回顾：Day 63–66 学了什么

```
Day 63（RAGAS 入门）：
  用"感觉答得不错"之外的量化指标（忠实度/答案相关性/上下文精度/上下文召回率）评估 RAG 系统
  第一次跑出了明确的数字，能说清楚系统当前最弱的环节是检索还是生成

Day 64（评估集与持续评估）：
  把"跑一次评估"固化成"可重复运行的资产"——20条评估问题 + 基准报表 + 回归对比机制
  评估集能持续吸收 Day 55 反馈追踪发现的真实失败 case，越来越贴近生产真实问题

Day 65（文档解析进阶）：
  意识到 RAG 流程最上游的数据质量问题——pdfplumber 处理不好表格和复杂排版
  用 Docling/marker 这类版面分析工具重新解析，明显提升表格抽取质量

Day 66（RAG 深化版整合）：
  把混合检索、Reranker、评估体系整合进 Day 20 系统，并引入 Agentic RAG
  让检索从"固定发生一次"升级为"自主判断、按需重试"，跑出整合前后的量化指标对比
```

这一周的主线是"从有量化指标，到有可持续运行的评估资产，到往上游数据质量排查，最后整合成一个真正升级的系统"——这也是整个路线 B（Day 58-67）"提升 RAG 质量"这条线的收尾一周。

## 二、复盘问题一：A/C/B 三条线，哪个提升最明显

### 2.1 三条线的核心产出回顾

| 路线 | 覆盖 Day | 核心产出 |
|-----|---------|---------|
| **A：LangChain/LangGraph/Agent** | 31–42 | LCEL 管道、StateGraph 编排、Checkpoint 持久化、Human-in-the-loop、MCP 工具标准化、跨会话记忆、多 Agent 协作 |
| **C：走向生产部署** | 43–57 | 可观测性、成本控制（缓存/批处理/路由）、模型网关、限流、上下文工程、状态管理、安全防护（注入攻防/护栏）、反馈追踪、容器化部署 |
| **B：提升 RAG 质量** | 58–67 | 混合检索、Reranker、HyDE、查询改写、RAGAS 评估体系、评估集持续化、文档解析进阶、Agentic RAG |

### 2.2 判断"提升明显"的标准

这是一个需要结合**自己项目实际短板**回答的问题，不存在标准答案，但可以用统一的判断标准替代"凭感觉"：

```
标准 1：这条线解决的问题，在我的项目里是否真实存在过？
  （比如从没遇到过多 Provider 切换需求，路线 C 的网关收益就有限；
    从没遇到过检索找不到专有名词的情况，路线 B 的混合检索收益也有限）

标准 2：这条线补齐后，是否有量化数据支撑"确实变好了"？
  （路线 B 有 RAGAS 指标；路线 C 有 Day 57 的生产就绪度检查清单；
    路线 A 可以用 Day 42 的 Agent 行为评估框架量化）

标准 3：如果去掉这条线的产出，项目会立刻暴露出什么问题？
  （去掉路线 A 的编排能力，复杂任务会退回手写 while 循环的脆弱状态；
    去掉路线 C 的安全护栏，项目直接不能上线；
    去掉路线 B 的检索优化，专业术语类问题答不准）
```

### 2.3 自查清单

```
□ 我的项目当前最大的用户痛点是什么？（答不准 / 不安全 / 跑不起来 / 任务处理不了）
□ 三条线里，哪条线的产出直接对应这个痛点？
□ 这条线整合后，是否用量化指标验证过确实解决了？
```

**这份自查清单没有替你给出答案**——因为"哪条线提升最明显"完全取决于每个项目具体的应用场景和短板分布，一个知识库客服项目可能路线 B（RAG 优化）收益最大，一个多步任务处理助手可能路线 A（Agent 编排）收益最大，一个已经对外提供服务的项目可能路线 C（生产部署）是刚需——按 2.1/2.2 节的标准对照自己的项目逐条判断，比直接采纳任何一个"通用答案"更可靠。

## 三、复盘问题二：要不要进入第四阶段

### 3.1 plan.md 第四阶段的原始提醒

`plan.md` 对第四阶段（私有化部署与量化、模型微调、多模态）有一条明确的取舍提醒：

> ⚠️ 对纯应用开发岗，本阶段优先级**低于**把二、三阶段的 RAG/Agent 做深。多数业务问题应先用"更好的 Prompt + RAG + 工具"解决，微调是最后手段。

### 3.2 判断标准与决策树

```
判断标准（对应 plan.md「六、下一步」的原文）：

  如果 A/C/B 三条线都已经做到"能给别人演示、有数据支撑"的程度
    → 可以按需进入第四阶段（私有化部署、LoRA 微调、多模态）

  如果某条线明显还是短板
    → 继续在这条线上加深，而不是急着往第四阶段扩展
```

```
决策树：

是否有明确的业务场景需要私有化部署/微调？（数据隐私要求、成本必须大幅降低、需要行业专有能力）
  │
  ├─ 是 → 评估 Day 62/64 的判断标准是否已经把 Prompt+RAG+工具的空间用尽
  │         （如果还没用尽，先把这些做深，微调往往解决不了"检索质量差"这类问题）
  │
  └─ 否 → 大概率不需要进入第四阶段
           三条线里找到自己项目的短板继续加深即可（参考 2.3 节自查清单）
```

**核心原则**：第四阶段不是"学完前三阶段后自然而然该学的下一步"，而是"遇到了前三阶段解决不了的具体问题（数据隐私、成本极限、领域适配）才该考虑的选项"——这和 Day 52、Day 57 反复强调的"规模信号判断"是同一套方法论在更大尺度上的应用。

## 四、深化阶段（Day 31–66）总结

### 4.1 三条路线核心产出速览

```
路线 A（Day 31-42）：把 Day 25 手写 ReAct 循环，升级为
  LCEL 管道 + StateGraph 编排 + Checkpoint 持久化 + Human-in-the-loop 审核 +
  MCP 工具标准化 + 跨会话记忆 + Planner/Executor/Critic 多 Agent 协作

路线 C（Day 43-57）：把"能力完备但生产不可维护"的 Agent，升级为
  可观测（LangFuse）+ 成本可控（缓存/批处理/路由）+ 架构统一（网关+限流）+
  上下文/状态健壮（Context Engineering + 外部化状态）+
  安全防护（注入攻防+输出护栏）+ 反馈闭环（Feedback Tracking）+ 可部署（Docker+CI）

路线 B（Day 58-67）：把 Day 20 的基础 RAG 系统，升级为
  混合检索 + Reranker + HyDE + 查询改写 + RAGAS 量化评估 + 持续评估集 +
  文档解析进阶 + Agentic RAG 自主检索决策
```

### 4.2 五个认知转变

```
1. 从"框架是拿来炫技的"到"框架解决的是手写代码在状态/持久化/协作上的具体痛点"
   —— Day 37 复盘时就已经明确：不该为了用最新技术而引入框架

2. 从"能跑的 Demo"到"能被观测、能控成本、能扛并发的系统"
   —— Day 52 的隐性成本框架，把"生产可维护性"拆解成了可以逐项对照的具体能力

3. 从"防注入靠一句 System Prompt 叮嘱"到"四层防御纵深（Prompt强化+输出校验+工具隔离+人工确认）"
   —— 安全不是写一条规则就完事，而是需要多层互相补位的防线

4. 从"检索用向量相似度就够了"到"召回不到 vs 排序不准是两类问题，需要不同手段"
   —— Day 62 的判断框架让检索优化从"随便加一招试试"变成"对症下药"

5. 从"感觉答得不错"到"用 RAGAS 量化指标 + 持续评估集验证每一次改动"
   —— 评估驱动贯穿了 Day 63-66，把主观判断替换成了可复现、可追踪的数字
```

## 五、深化阶段常见误区回顾

深化阶段路线图里记录的九条误区，值得在结束时再过一遍（详见 [`day31_67_deepening_roadmap.md`](../规划文档/day31_67_deepening_roadmap.md) 第五节）：

```
1. 框架崇拜——不是为了用最新技术，而是解决具体痛点
2. 跳过 LangChain 直接学 LangGraph——LangGraph 建立在 LCEL 之上
3. 工程化架构一步到位——按 Day 52 标准判断值不值得投入
4. 可观测性拖到最后才补——应该在功能稳定后立刻补上
5. 只优化检索不评估——任何优化都要有数字支撑
6. 安全防护一次性做完就不管——红队测试应该是常规检查项
7. 反馈收集了但没有回流——收集了不用等于没做
8. 批处理和缓存/路由混为一谈——三者省的是不同的钱
9. Agent 过度设计——多数问题不需要多 Agent 协同
```

这九条误区的共同本质：**深化阶段学的每一项能力都有明确的适用边界和引入信号，"多学了一项能力"不等于"该无脑用上"**——这也是贯穿 Day 52/57/62/67 所有复盘日的核心方法论。

## 六、下一步去哪里

按 `plan.md` 的建议，深化阶段结束后有几条候选路线，选择依据是 2.1-3.2 节的自查结果：

```
候选 1：某条线（A/C/B）仍是明显短板 → 继续在这条线上加深
  例如：Agent 编排能力够用，但检索质量依然是用户痛点 → 回到路线 B 继续打磨
        （比如深挖 Reranker 模型选型、扩充评估集覆盖场景）

候选 2：三条线都已经"能演示、有数据支撑" → 可以按需评估第四阶段
  例如：明确有数据隐私要求必须私有化部署 → 参考 plan.md 第四阶段
        （Ollama/vLLM 私有化部署、LoRA/QLoRA 微调、多模态拓展）

候选 3：三条线都够用，且没有第四阶段的明确业务需求 → 转向横向深化或新方向
  例如：把当前项目真正推向生产使用、持续收集真实反馈（回到 Day 55 的反馈闭环机制）
        用真实用户数据反过来验证和迭代已经学过的全部能力
```

**判断标准**：不要因为"路线图上还有第四阶段"就机械地继续往下学——回到 2.3 节的自查清单，先确认当前项目的真实短板在哪里，再决定下一步投入的方向。

**技能查缺补漏补充篇**：深化阶段主线之外，如果发现某项通用工程技能一直没covered（比如求职市场常问、但路线图没覆盖的内容），可以作为不计入主线天数的补充篇追加，参考 [Day 68 · FastAPI 后端工程](day68_fastapi_backend.md)（把 LLM/RAG/Agent 应用从"界面内嵌调用"升级为"独立后端 API 服务"）。

## 七、深化阶段学习结束语

从 Day 31 到 Day 67，这 37 天做的事情，本质上是把 Day 1-30 那个"能跑、但只有 Agent 能力、没有工程化护城河"的项目，一点点补齐成一个真正经得起真实场景考验的系统——先补框架编排能力（路线 A），再补生产工程化的九项硬指标（路线 C），最后把 RAG 检索这个最容易被忽视但影响巨大的环节做深做透（路线 B）。

如果说 30 天路线教会的是"怎么把一个大模型应用从零跑起来"，那么这 37 天教会的是"怎么判断一个能力值不值得加、什么时候该加、加了之后怎么验证它真的有用"——这种判断力比记住某个具体 API 怎么调用更重要，也是贯穿整个深化阶段所有复盘日反复强调的核心方法论。

深化阶段到此结束，接下来的方向留给 2.1-3.2 节的自查结果来决定。
